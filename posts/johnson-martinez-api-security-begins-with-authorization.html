API Security Begins with Who Can Access Which Record

Authentication tells an API who is calling. Authorization must still decide which records and actions that caller is allowed to access.

Cybersecurity · APIs · Privacy · Software · Research

A valid login is not a permission slip for every record

Many applications correctly ask users to sign in and still expose data they should not see. The common mistake is treating authentication as if it automatically grants access to every object in the system. An API must make a separate authorization decision for each sensitive record and action.

Understand broken object-level authorization

OWASP’s API Security Top 10 identifies Broken Object Level Authorization as a major API risk. It occurs when an endpoint accepts an object identifier but fails to check whether the authenticated user is allowed to access that specific object. If a customer can change an invoice ID in a request and retrieve another customer’s invoice, the API has an authorization problem even though the attacker is logged in.

Check ownership on the server

Do not rely on a hidden button, a disabled menu item or a random-looking identifier in the browser. The server should derive the user’s identity from a trusted authentication context and enforce access rules against the requested record. A database query can scope records to the current account rather than fetching any object by ID and hoping the front end prevents misuse.

Test roles and object boundaries

Create tests for two ordinary users, an administrator and any special roles in the product. Check whether one user can read, edit, delete or export another user’s data. Test nested resources too: a user may be allowed to see a project but not every file, member record or billing detail associated with it. Include negative tests that prove forbidden access is rejected.

Limit what an endpoint returns

Authorization is not the only concern. Avoid returning unnecessary personal or business information. Validate input, limit request rates and expensive operations, handle errors without exposing internal details, and maintain an inventory of API versions and endpoints. OWASP’s API guidance also covers broken authentication, property-level authorization, unrestricted resource consumption, security misconfiguration and unsafe consumption of APIs.

Protect the full data path

API security should include the application, database, logs, backups and third-party services. Do not place secrets in client-side code. Use least-privilege service accounts, rotate credentials when exposure is suspected and monitor unusual access patterns. Logs should help investigate incidents without unnecessarily copying sensitive personal data into another system.

A small verification exercise

Pick one endpoint that returns a user-specific record. Sign in as User A and retrieve a record owned by User A. Then try the same request as User B using the same record identifier. User B should receive a safe denial or not-found response, and the attempt should be logged appropriately. Repeat for update and delete actions. This simple exercise can reveal a class of weaknesses before they become a public incident.

Authorization is a product requirement

The right question is not only “Who are you?” It is “Are you allowed to perform this action on this exact record, at this moment?” Making that check explicit protects users, supports privacy obligations and gives developers a clearer security model.
